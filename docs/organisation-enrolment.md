# Organisation enrolment

## Current organisation partner workflow

Partners use one Firebase email/password login across `/partnerships` and `/organisation-enrolment`. The browser uses the named `falowen-partners` Firebase app so partner sign-in/sign-out does not replace a learner or Admin session. The representative verifies their email, saves one organisation profile, signs the existing agreement once and waits for Falowen approval. Approved partners then submit students through the same account; subsequent visits show their profile and agreement status, not another registration or signing request. Public agreement text and the unsigned sample remain readable without signing in.

`organisationPartners/{id}` is the permanent profile; `organisationPartnerMembers/{uid}` authorizes its verified login. The ID preserves the existing `organisation-v5:` normalized-email hash for historical compatibility and is not recomputed for phone/contact-name updates. Email and legal-name corrections require owner verification; self-service changes are limited to contact name and phone. Neither company name, phone, request body ID nor session storage grants access. Exact earlier company-name matches and normalized reserved names stop new registration for manual review; the directory flags matching names across different emails without merging or exposing profiles publicly. Similar spellings still require staff judgment.

### Existing organisations and account setup

On `/organisation-submissions`, the owner verifies the historical contact, then chooses **Prepare partner account / send setup email**. The backend requires the verified owner, resolves existing agreements/submissions by that exact email, creates or reuses the Firebase login and saves membership under the existing organisation ID. Preparation is repeat-safe. New logins receive a random unexposed password; existing credentials, verification status and roles are not overwritten. The browser requests Firebase's password-reset/setup email only after successful preparation. It does not display or email a password. If email delivery fails, preparation remains saved and the owner can retry or the partner can use **Set password / forgot password?**. Email verification is still required after password setup. Do not claim an invitation was sent merely because a login was created.

Existing agreements, students, tuition, payments, student codes and Auth UIDs are not rewritten or merged. A legacy partner without a signed agreement must sign it; a pending partnership still needs owner approval before new student submissions. Historical submissions are visible through a bounded, on-demand partner endpoint. It returns only that verified profile's student names, levels and review states; no other organisation's batches or private payment/student fields. Up to 50 batches are shown, with truncation disclosed.

New partner-only membership stores `courseAccessAllowed: false`. Only an already UID-linked student retains course-user access through membership; existing staff access is preserved by the learner rules. Deploy the learner `courseUser()` membership restriction before enabling partner registration/activation. These new collections remain server-only under default-deny rules. No client membership writes, scheduled jobs, background polling, new email webhook or automatic bulk invitation is introduced.

The enrolment API now requires a verified member and an approved signed agreement. It takes company details and agreement ID from the server-owned profile, ignores client identity overrides and rejects cross-organisation request-ID replay. Public unauthenticated submissions are intentionally no longer accepted after rollout. Staff review, billing and account invitation for students continue as before.

## Readable student codes and existing organisation records

Organisation approvals retain the stable internal Firestore document ID `ORG-<hash>` as the linked `studentId`, so payment allocations, Firebase UID linking and audit references remain valid. Their **public student code** is now the normal `FirstLast###` format: name characters plus a deterministic three-digit suffix, with server-side collision checks. New records store it in both `studentCode` and `studentcode`, and the review list exposes a separate `displayStudentCode`.

Old approved records may still display the internal `ORG-` ID. The owner's **Fix student code** action on `/organisation-submissions` updates only the readable code fields, updates the review row's display value, adds an audit entry and requests the existing learner-side student-sheet upsert. It does not rename the Firestore document, create a second student, change the Auth UID, alter payment references, change tuition/balance/contract dates or send receipts. The learner Sheets writer matches the existing sheet row by email as well as code, preventing a second row when the public code changes. The learner-side sync must deploy its fix to prefer verified `paid` over `initialPaymentAmount`, which is a payment intent; otherwise the sheet may show 0 received even when the canonical student payment is nonzero. Inspect the live student ledger and spreadsheet after using the repair action rather than hand-overwriting a sheet row.

## Unexpected HTML response

The client reads response text and validates JSON before accepting success. An HTML fallback, empty response or network failure keeps all form entries and the original request ID available for retry. The Vercel proxy converts non-JSON organisation API replies to a JSON 502 instead of forwarding HTML. Do not treat this message as confirmation of a saved submission; only a reference receipt confirms it.

Regression coverage: `tests/organisation-enrolment-request.test.js` covers public submissions, retries, owner-token handling, list/review methods, validation errors, network errors, HTML/empty replies and actual Vercel router dispatch to the Firebase proxy. Backend tests cover validation, duplicates, approval, rejection, access control, idempotency and quotas.

## Delete submissions

The owner can choose **Delete submission** and confirm. This removes the submitted organisation/student details from the batch and hides it from the queue. Approved student documents, Firebase accounts and sheet rows remain untouched. A minimal deletion marker retains the reference, original creation time and deletion audit metadata so an old public retry cannot recreate the batch. Review of a deleted submission returns 404. Deleting the same reference again is safe.

## Historical partnership and referral programme (closed to new applications)

The public `https://www.falowen.app/partnerships` page links institutions to the existing group form. Referral applicants use a separate form, accept the versioned terms and enter the owner queue at `/referral-review` (Students → Referral applications and commissions). Verify the contact before approval, then send the approved link to the contact manually. Repeated applications and approvals preserve the original record and invitation.

Learners open the partner link, consent to matching their email, then continue to the regular Campus signup with that email. The first invitation registered for an email retains attribution. An invitation creates neither a student account nor a payment. Check attribution with the learner before approving a commission.

Open the owner queue on demand. Inspect the earliest completed tuition payment for the learner across Admin payment links and Campus webhook records. Confirm the learner’s identity, any earlier offline payments and disputes. Approval verifies the selected reference, student metadata, payment time, tuition and refunds directly with Paystack using the existing bound PAYSTACK_SECRET. The commission is 10% of tuition on the first completed payment, rounded to the nearest pesewa. A refunded first payment cannot be replaced with a later instalment. The ledger excludes institutional enrolments and self-referrals. Cash payments alone have no provider record to verify and require separate manual handling outside this ledger.

After paying a partner externally, record the payout receipt once. Use **Recheck refund with Paystack** on later review or **Cancel referral / record refund** for an offline decision. A subsequent refund cancels the commission and retains the payout history for recovery. Refund rechecks run on demand. The programme adds no scheduled jobs, public collection reads, automatic emails or money transfers.

## Organisation Paystack payments

Owner-only route `/paystack` is linked from Students and each organisation submission. Load submitted organisations (including older pages), select approved students and enter the amounts covered by the institutional agreement. Configure canonical student tuition balances, class and contract in Students first. The server rejects unknown students, different organisations, duplicate students and amounts above the outstanding balance.

The invoice stores the company billing/receipt email, agreement reference, creator, each student's gross amount and fixed GHS discount, plus a required discount reason. Discounts reduce balances separately from actual `paid` tuition. Checkout applies the existing processing-share calculation to net tuition. Generating a link does not credit accounts. One persisted request reference prevents UI network retries from creating different invoice records; changing invoice details starts a new reference. Avoid issuing multiple outstanding invoices for the same tuition obligation.

After signed `charge.success` validation, a single Firestore transaction credits all approved students, records discounts, updates explicit balances, marks their `status: Active` and `paymentStatus: Paid` or `Partially Paid`, and creates per-student allocation records for history. The same student write sets `syncedToSheets: false`, so the existing learner-side Firestore sync updates the **same** Students sheet row (including organisation payer details). No extra spreadsheet polling, subscription or sheet-only payment is needed. Duplicate delivery does not credit twice.

For first partial payments via the organisation Paystack link, the server records one calendar month of access from the verified Paystack receipt date, using the same terms as verified manual partial tuition. A fully paid student is marked Active and records the six-month term, but the six-month **start** must be set by the existing actual account-activation flow rather than from the payment timestamp. An already assigned `className` remains untouched. The untrusted `requestedClassName` is **never** silently used as a class assignment: `organisationClassAssignmentPending` flags missing approval for the owner. Firebase UID creation and secure invitation remain separate from financial confirmation; the payment webhook does not impersonate a student, create accounts with unverified matching emails or email passwords.

The signed Paystack webhook attempts the existing one-time company receipt after committing the payment. A retry of the *same* webhook can retry a failed receipt (using the stored reference and delivery lease) without double-crediting or creating a duplicate ledger. Receipt send failure does not undo paid student accounts. The company receives the financial receipt; students receive distinct enrolment confirmation after account setup/class approval. Existing student update/sheet triggers receive these canonical updates (`syncedToSheets: false`); Firebase account activation and agreed contracts remain staff-managed. Group payment and allocation records are explicitly ineligible for referral commission. No new public payment-data endpoint or scheduled job is added.

The company receipt contains the payment reference, student breakdown, discounts, net tuition and checkout total. It uses the existing payment-update/announcement webhook configuration. For future receipts the Admin payload also includes an explicit short subject and a versioned `receipt_payload_json` field with verified payment totals, dates, student allocations, outstanding balance and access end. Deploy the companion Falowen Announcement Apps Script renderer (with `receipt_payload_json` in its optional columns and `organisation_payment_receipt` handling) to render a branded amount-first HTML receipt without the internal legacy arrangement paragraph or generic `Announcement:` prefix. Update the Apps Script **before** or alongside the Admin backend. A previously `sent` payment is idempotent: a template update never resends the same receipt, changes student credits, or rewrites earlier inbox messages. A receipt failure leaves paid credits intact; Paystack webhook retries or the owner's **Retry company receipt** action retry delivery. **Verify with Paystack** reuses existing authenticated provider reconciliation if a webhook was missed, then attempts the company receipt. History refresh reads recorded status; it does not itself verify payment. Student payment-update emails continue independently. A delivery lease suppresses overlapping receipt retries; a crash after external email delivery but before saving its sent marker can still cause a duplicate email. Payment credits remain idempotent.

Deploy the Admin Vercel app and Firebase backend together. Existing build/deploy payment patches register `functions/organisationPayments.js`; preserve the generated-payment integration in `scripts/patchStudentPaymentLinks.mjs`, rather than editing its generated index block. The Paystack secret and signed-webhook URL remain the existing ones. No live money is charged by these tests. Verify a test-mode group payment, company email delivery and learner/sheet balance display before enabling production use.

Validation: `node --test functions/organisationPayments.test.cjs functions/organisationEnrolment.test.cjs functions/referralProgramme.test.cjs`; existing student payment patch tests; `npm run build`.

## Verified legacy manual organisation payments (November 2026)

For institutions whose original agreement required **full tuition to Falowen** and whose money was already received by direct bank transfer, mobile money or cash, open `/organisation-submissions`, approve the student, configure the student's real tuition and outstanding balance in Students, then choose **Record manual payment** next to the submission. This opens `/paystack?batch=<id>&mode=manual` with a separate form; it does **not** create a Paystack checkout or apply the new first-tuition 10% organisation-share rule. The form explicitly supports `legacy_full_tuition` only, not new agreements. Confirm the historical agreement independently if the directory says "Not linked"; the form records a descriptive note and does not fabricate an electronic signature.

The owner must check the actual bank/MoMo/cash statement independently, then enter the payment method, the **real** external transaction or cash receipt reference, receipt date, original agreement note, verification note and explicit verification confirmation. The server enforces owner Firebase token permissions, an approved student linked to the selected batch, configured tuition and outstanding balance, zero discount, and a positive payment amount not greater than the outstanding balance. Confirmation is an owner attestation, **not automatic provider reconciliation**. An external reference is hashed together with the method to create one stable global manual-payment document; a retry with identical details is read-only and conflicting reuse returns HTTP 409. Distinct transaction references must still be checked manually against the actual bank statement to avoid human double-entry.

One Firestore transaction creates the owner-verified manual payment ledger and per-student allocations, credits the canonical student `paid` amount, subtracts only the verified payment from the outstanding balance, sets `paymentStatus: Partially Paid` while money remains due (or `Paid` when fully settled), flags `syncedToSheets: false`, and records the bank/reference metadata. No discount, referral commission, Paystack fee or second charge is created. For partial payments with no pre-existing contract dates, the one-month access term starts on the actual payment receipt date, recorded in `contractStart` and `contractEnd` with `contractTermMonths: "1"`. The student remains uninvited until staff prepares the login. Existing contract dates block automatic partial-access changes so staff can review them. For example, GH₵2,000 received of GH₵3,000 tuition leaves GH₵1,000 outstanding. Merely editing payment status in Students is **not** a replacement for a ledger entry.

After committing student credits, the server attempts an organisation receipt to the **registered organisation contact email** using the existing notification webhook. The receipt states verified manual payment, external reference, agreed course tuition, actual amount received, remaining balance and one-month end date (when partial), and GHS 0.00 partner deduction; it must not call a partial payment full settlement. A delivery failure does **not** unwind credits; it is visible as `receiptStatus: failed` with a **Retry company receipt** action. Retries now return owner-safe, actionable email configuration / unreachable-provider / provider-HTTP diagnostics instead of the generic Payment service unavailable message; the payment document stores only a safe `receiptErrorCode` (not provider secrets or raw response bodies). The payment history offers **Copy company payment confirmation for manual email** for verified manual records when delivery is not confirmed. This copies a clearly labelled manual confirmation with the original payment reference, tuition received and outstanding balance; it does not create a new charge, claim the automatic email succeeded, or issue a new payment receipt number. An existing sent marker suppresses duplicate retries. No student payment-update email is triggered for organisation-funded tuition; a separate enrolment confirmation occurs after invitation readiness. For partial tuition (such as GH₵2,000 against GH₵3,000), that student confirmation explicitly states the remaining GH₵1,000 and one-month access end date rather than claiming the standard six-month full-paid contract. No new recurring job or extra service is introduced.

Manual routes: owner-only `POST /api/payments/organisations/manual`; receipt retry `POST /api/payments/organisations/receipt/:reference`; existing GET `/api/payments/organisations/:batchId` includes manually recorded payments. The existing Vercel `/api/payments/(.*)` rewrite already proxies these routes to the Firebase function. The Firebase function and Admin frontend must be deployed together. Tests verify duplicate references, partial and full balances, one-month access, owner authorization, receipt retries, safe email error classifications and preserved student credits.

## Existing terms, electronic consent and signed PDF receipts

The public `/partnerships` page preserves its published institutional and 10% referral wording. The separate signing form loads that exact server-owned snapshot (`partnership-2026-11-05-v2`) before submission, collects the representative's contact details, typed name and explicit agreement/electronic-signature consent, and saves an immutable receipt immediately bearing the applicant's typed signature and the pre-authorised Falowen director signature. This receipt records consent and submission; it is not partner approval. An unsigned sample is downloadable before signing. Institutional signers can continue to the organisation student form after saving.

The completed PDF and a hash of its random receipt capability are stored in server-only `partnershipPrivate`; no public listing or email-only retrieval is provided. Browser downloads POST the capability in the body, use no-store responses, and contain no bank account number. The owner can download the identical receipt from `/referral-review`. Pending legacy applications can be upgraded by signing; an already signed or approved application cannot be overwritten publicly. A lost receipt capability requires contacting Falowen for an owner-provided copy.

Install the authorised private PNG once through the signature upload on `/referral-review`, or configure `PARTNERSHIP_SIGNATURE_DRIVE_FILE_ID` with the existing director-signature Drive file and grant the actual Firebase function runtime service account read access to it. Drive access must be explicitly provisioned; the developer's connected Drive session is not the function's credential. Raw PNG bytes are stored in server-only `partnershipSettings`, not GitHub or public assets. A missing signature blocks signing before accepting an application. Replacing the signature affects future receipts only. An authenticated owner is required for installation and private receipt copies.

Referral applications additionally collect Ghana bank or mobile money payout details and separate payout-data consent. Full details are AES-256-GCM encrypted with a context-specific HKDF key derived from the bound `PAYSTACK_SECRET`, then stored only in `partnershipPrivate`. Application lists expose a masked destination. Coordinate Paystack-secret rotation with decrypting/re-encrypting existing pending account data using the previous key; do not simply discard the old key. Signed receipts never expose full payout details.

After partner approval, the owner verifies the identity/destination, then chooses **Verify payout destination and enable commissions**. Paystack account resolution must match the account number and holder name before creating a GHS transfer recipient. Name mismatches fail closed for correction. Signing alone neither approves the partner nor enables money movement. The approved-partnership event sends the unique referral link by the existing announcement/payment email service; repeated events use a delivery marker (an email can still duplicate if a crash happens after delivery but before saving the marker).

## Historical automatic eligible commissions

Automation is implemented behind `REFERRAL_AUTO_PAYOUTS_ENABLED=true`, disabled by default. Event-driven Functions observe completed Admin payments and Campus Paystack webhook records; there is no new cron or polling loop. Only an approved current signed referral partner with a verified enabled payout destination qualifies. Signup alone does not earn anything. The first eligible tuition payment across both existing ledgers is checked directly with Paystack and its refund records, and the commission is 10% of that first tuition amount, in pesewas. Later instalments, renewals, sponsorship, self-referrals, ambiguous offline history and refunded payments cannot generate automatic payouts. The student commission lock prevents another claim earning for the same student.

A deterministic transfer reference is persisted before calling Paystack. Unknown outcomes are verified against that same reference; they never generate a second transfer. The payout stays `pending`, `otp` or `needs_review` until provider confirmation; only verified success records it paid. Signed transfer/refund events use the existing direct Firebase Paystack webhook and are checked against the stored reference, amount, currency and recipient. A refund cancels the commission; a completed/in-flight payout is flagged for owner recovery rather than silently debiting the partner. Provider failures, funding and OTP requirements remain visible for owner review. The owner can recheck a claim on demand; enabling a destination also checks up to 100 existing claims. Older/backlogged claims beyond this bound require owner review.

Production setup requires Paystack Transfers enabled for the merchant, sufficient Paystack balance and compatible transfer-approval settings, the existing signed webhook configured for transfer/refund events, private director-signature setup and the email webhook. Do not advertise live automatic payouts until test-mode checkout → commission → transfer → receipt/refund has been verified. Deploy the Admin Firebase API and new event triggers before the learner public form/route updates. Retain server-only rules for `partnershipPrivate`, `partnershipSettings` and notification markers; never deploy unrelated Firestore rules blindly.

## Organisation portal design and 10% agreement

The public organisation page has three accessible tabs: Overview, Agreement and Register, with navy/cream/amber styling. It contains no individual signup section or extra student-list link before signing. Registration details remain mounted when navigating back to read the agreement. The Register success panel alone provides the student-list continuation link. The agreement is loaded on demand; registration is withheld if the backend does not advertise the updated 10% invoice-deduction terms. There is no polling or public signature endpoint.

Version 5 specifies 10% of each approved student's first tuition payment, excluding processing fees; later instalments and renewals do not earn another share. Admin can use **Apply 10% organisation share** to fill the existing per-student deduction amounts, then review the invoice before generating the link. Staff must check payment history before applying a first-payment share. Net tuition and retained deductions continue to be stored separately. Older version 3 signed documents and approval notifications remain supported without rewriting PDFs. No separate payout, bank collection or Paystack split is introduced.
