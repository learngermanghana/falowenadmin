# Organisation enrolment

## Current organisation partner workflow

The public `/partnerships` page is one programme for education consultants, travel agencies and organisations. The organisation signs the agreement and immediately downloads its receipt with both signatures, then follows the organisation student-list form. Its contact details and signed agreement reference are carried into that form through browser session storage. If that storage is unavailable, contact details can still be entered manually. A submitted signed reference is checked server-side against the organisation contact email; previous unsigned-reference submissions remain supported for compatibility.

Falowen reviews and approves the submitted students, prepares their tuition/class/contract details and creates one group Paystack link. The agreed partner share is a fixed GHS invoice deduction per student: gross tuition minus retained partner share equals tuition paid to Falowen, plus the displayed existing processing share. No Paystack split, bank details or separate commission payout is needed for this programme. The company receipt shows net tuition and each retained share; cash and deductions remain separately recorded. Verified payment updates student balances; staff complete account invitations/enrolment after payment. The agreement reference pre-fills on the Admin invoice screen.

Clients paying for themselves use normal signup and pay the full advertised tuition without earning any partner commission. New referral applications/claims are closed (HTTP 410), old referral links lead to normal signup, and legacy pending referral applications cannot be newly approved. Historical signed PDFs and commission/refund audit records are retained; they are not rewritten or silently deleted. The historical sections below describe legacy behaviour, not the new organisation programme. New organisation receipts use `organisation-partnership-2026-11-05-v5`; older stored receipts remain unchanged.

Public route: `https://www.falowen.app/organisation-enrolment`. No organisation login or CSV upload. The organisation enters contact details once, types student rows or pastes tab-separated cells, and submits up to 50 students. Blank rows are ignored; name, student email, phone and level are required. No prior submission or student data is readable publicly. The same public URL can be reused for future groups.

Owner review route: `/organisation-submissions`, linked from Students. Load recent batches, page through older ones, and approve/reject each student. Verify the organisation, permission, agreement and payment arrangement before approval. Organisation identity is self-reported. A verified owner ID token is required server-side for reads and review, matching existing account activation permissions.

Approval atomically creates one pending student and records its ID against the row. An email duplicate blocks approval and requires manual review in Students. Repeated approval does not create more records. Rejection creates no student or login. No payment is marked paid based on the organisation's submission. `billingResponsibility: organisation` and organisation contact details record who pays; existing contract/fee tooling still requires staff configuration. This does not yet introduce organisation invoicing or change all existing payment reminder systems.

Use **Manage student / send invitation** to open the student directory filtered by email. Configure the student's agreed class, contract, payment status and fees there, then use the existing activation panel to prepare the Firebase UID and request its password-setup email. No passwords are collected in the public form. Existing unlinked Firebase logins are rejected by account provisioning for manual investigation. Invitation state and first-sign-in state remain separate.

The learner repository's existing `onStudentCreated` / `onStudentUpdated` triggers deliver student records to the Students sheet. Approved records use their canonical student code and `syncedToSheets: false`; UID linking updates the same record. Sync begins at approval, and later setup updates sync through the existing update trigger. A submission alone does not write to students or the sheet. Verify live triggers after deployment rather than treating a frontend build as proof of delivery.

Backend: `functions/organisationEnrolment.js`, registered in the Admin `api` Firebase function; same-origin Vercel proxy in `api/router.js`. Deploy both Firebase and Vercel. Submission uses a client-generated request ID for safe retries, honeypot, explicit consent, server validation, row caps and atomic per-contact daily quota. The two new collections are server-only (existing default-deny rules); no public Firestore access is required. Quota documents contain hashed keys; expiry timestamps can use a Firestore TTL policy for housekeeping. No new scheduled job is installed.

Validation: `node --test functions/organisationEnrolment.test.cjs functions/studentAccountActivation.test.cjs tests/student-emergency-contact.test.js`; `npm run build`.

## Unexpected HTML response

The client reads response text and validates JSON before accepting success. An HTML fallback, empty response or network failure keeps all form entries and the original request ID available for retry. The Vercel proxy converts non-JSON organisation API replies to a JSON 502 instead of forwarding HTML. Do not treat this message as confirmation of a saved submission; only a reference receipt confirms it.

Regression coverage: `tests/organisation-enrolment-request.test.js` covers public submissions, retries, owner-token handling, list/review methods, validation errors, network errors, HTML/empty replies and actual Vercel router dispatch to the Firebase proxy. Backend tests cover validation, duplicates, approval, rejection, access control, idempotency and quotas.

## Delete submissions

The owner can choose **Delete submission** and confirm. This removes the submitted organisation/student details from the batch and hides it from the queue. Approved student documents, Firebase accounts and sheet rows remain untouched. A minimal deletion marker retains the reference, original creation time and deletion audit metadata so an old public retry cannot recreate the batch. Review of a deleted submission returns 404. Deleting the same reference again is safe.

## Historical partnership and referral programme (closed to new applications)

The public `https://www.falowen.app/partnerships` page links institutions to the existing group form. Referral applicants use a separate form, accept the versioned terms and enter the owner queue at `/referral-review` (Students → Referral applications and commissions). Verify the contact before approval, then send the approved link to the contact manually. Repeated applications and approvals preserve the original record and invitation.

Learners open the partner link, consent to matching their email, then continue to the regular Campus signup with that email. The first invitation registered for an email retains attribution. An invitation creates neither a student account nor a payment. Check attribution with the learner before approving a commission.

Open the owner queue on demand. Inspect the earliest completed tuition payment for the learner across Admin payment links and Campus webhook records. Confirm the learner’s identity, any earlier offline payments and disputes. Approval verifies the selected reference, student metadata, payment time, tuition and refunds directly with Paystack using the existing bound PAYSTACK_SECRET. The commission is 10% of tuition on the first completed payment, rounded to the nearest pesewa. A refunded first payment cannot be replaced with a later instalment. The ledger excludes institutional enrolments and self-referrals. Cash payments alone have no provider record to verify and require separate manual handling outside this ledger.

After paying a partner externally, record the payout receipt once. Use **Recheck refund with Paystack** on later review or **Cancel referral / record refund** for an offline decision. A subsequent refund cancels the commission and retains the payout history for recovery. Refund rechecks run on demand. The programme adds no scheduled jobs, public collection reads, automatic emails or money transfers.

## Organisation Paystack payments

Owner-only route `/paystack` is linked from Students and each organisation submission. Load submitted organisations (including older pages), select approved students and enter the amounts covered by the institutional agreement. Configure canonical student tuition balances, class and contract in Students first. The server rejects unknown students, different organisations, duplicate students and amounts above the outstanding balance.

The invoice stores the company billing/receipt email, agreement reference, creator, each student's gross amount and fixed GHS discount, plus a required discount reason. Discounts reduce balances separately from actual `paid` tuition. Checkout applies the existing processing-share calculation to net tuition. Generating a link does not credit accounts. One persisted request reference prevents UI network retries from creating different invoice records; changing invoice details starts a new reference. Avoid issuing multiple outstanding invoices for the same tuition obligation.

After signed `charge.success` validation, a single Firestore transaction credits all students, records their discounts, updates explicit balances and creates per-student allocation records for history. Duplicate delivery does not credit twice. Existing student update/sheet triggers receive these canonical updates (`syncedToSheets: false`); Firebase account activation and agreed contracts remain staff-managed. Group payment and allocation records are explicitly ineligible for referral commission. No new public payment-data endpoint or scheduled job is added.

The company receipt contains the payment reference, student breakdown, discounts, net tuition and checkout total. It uses the existing payment-update/announcement webhook configuration. A receipt failure leaves paid credits intact; Paystack webhook retries or the owner's **Retry company receipt** action retry delivery. **Verify with Paystack** reuses existing authenticated provider reconciliation if a webhook was missed, then attempts the company receipt. History refresh reads recorded status; it does not itself verify payment. Student payment-update emails continue independently. A delivery lease suppresses overlapping receipt retries; a crash after external email delivery but before saving its sent marker can still cause a duplicate email. Payment credits remain idempotent.

Deploy the Admin Vercel app and Firebase backend together. Existing build/deploy payment patches register `functions/organisationPayments.js`; preserve the generated-payment integration in `scripts/patchStudentPaymentLinks.mjs`, rather than editing its generated index block. The Paystack secret and signed-webhook URL remain the existing ones. No live money is charged by these tests. Verify a test-mode group payment, company email delivery and learner/sheet balance display before enabling production use.

Validation: `node --test functions/organisationPayments.test.cjs functions/organisationEnrolment.test.cjs functions/referralProgramme.test.cjs`; existing student payment patch tests; `npm run build`.

## Existing terms, electronic consent and signed PDF receipts

The public `/partnerships` page preserves its published institutional and 10% referral wording. The separate signing form loads that exact server-owned snapshot (`partnership-2026-11-05-v2`) before submission, collects the representative's contact details, typed name and explicit agreement/electronic-signature consent, and saves an immutable receipt immediately bearing the applicant's typed signature and the pre-authorised Falowen director signature. This receipt records consent and submission; it is not partner approval. An unsigned sample is downloadable before signing. Institutional signers can continue to the organisation student form after saving.

The completed PDF and a hash of its random receipt capability are stored in server-only `partnershipPrivate`; no public listing or email-only retrieval is provided. Browser downloads POST the capability in the body, use no-store responses, and contain no bank account number. The owner can download the identical receipt from `/referral-review`. Pending legacy applications can be upgraded by signing; an already signed or approved application cannot be overwritten publicly. A lost receipt capability requires contacting Falowen for an owner-provided copy.

Install the authorised private PNG once through the signature upload on `/referral-review`, or configure `PARTNERSHIP_SIGNATURE_DRIVE_FILE_ID` with the existing director-signature Drive file and grant the actual Firebase function runtime service account read access to it. Drive access must be explicitly provisioned; the developer's connected Drive session is not the function's credential. Raw PNG bytes are stored in server-only `partnershipSettings`, not GitHub or public assets. A missing signature blocks signing before accepting an application. Replacing the signature affects future receipts only. An authenticated owner is required for installation and private receipt copies.

Referral applications additionally collect Ghana bank or mobile money payout details and separate payout-data consent. Full details are AES-256-GCM encrypted with a context-specific HKDF key derived from the bound `PAYSTACK_SECRET`, then stored only in `partnershipPrivate`. Application lists expose a masked destination. Coordinate Paystack-secret rotation with decrypting/re-encrypting existing pending account data using the previous key; do not simply discard the old key. Signed receipts never expose full payout details.

After partner approval, the owner verifies the identity/destination, then chooses **Verify payout destination and enable commissions**. Paystack account resolution must match the account number and holder name before creating a GHS transfer recipient. Name mismatches fail closed for correction. Signing alone neither approves the partner nor enables money movement. The approved-partnership event sends the unique referral link by the existing announcement/payment email service; repeated events use a delivery marker (an email can still duplicate if a crash happens after delivery but before saving the marker).

## Historical automatic eligible commissions

Automation is implemented behind `REFERRAL_AUTO_PAYOUTS_ENABLED=true`, disabled by default. Event-driven Functions observe completed Admin payments and Campus Paystack webhook records; there is no new cron or polling loop. Only an approved current signed referral partner with a verified enabled payout destination qualifies. Signup alone does not earn anything. The first eligible tuition payment across both existing ledgers is checked directly with Paystack and its refund records, and the commission is 10% of that first tuition amount, in pesewas. Later instalments, renewals, sponsorship, self-referrals, ambiguous offline history and refunded payments cannot generate automatic payouts. The student commission lock prevents another claim earning for the same student.

A deterministic transfer reference is persisted before calling Paystack. Unknown outcomes are verified against that same reference; they never generate a second transfer. The payout stays `pending`, `otp` or `needs_review` until provider confirmation; only verified success records it paid. Signed transfer/refund events use the existing direct Firebase Paystack webhook and are checked against the stored reference, amount, currency and recipient. A refund cancels the commission; a completed/in-flight payout is flagged for owner recovery rather than silently debiting the partner. Provider failures, funding and OTP requirements remain visible for owner review. The owner can recheck a claim on demand; enabling a destination also checks up to 100 existing claims. Older/backlogged claims beyond this bound require owner review.

Production setup requires Paystack Transfers enabled for the merchant, sufficient Paystack balance and compatible transfer-approval settings, the existing signed webhook configured for transfer/refund events, private director-signature setup and the email webhook. Do not advertise live automatic payouts until test-mode checkout → commission → transfer → receipt/refund has been verified. Deploy the Admin Firebase API and new event triggers before the learner public form/route updates. Retain server-only rules for `partnershipPrivate`, `partnershipSettings` and notification markers; never deploy unrelated Firestore rules blindly.

## Organisation portal design and 10% agreement

The public organisation page has three accessible tabs: Overview, Agreement and Register, with navy/cream/amber styling. It contains no individual signup section or extra student-list link before signing. Registration details remain mounted when navigating back to read the agreement. The Register success panel alone provides the student-list continuation link. The agreement is loaded on demand; registration is withheld if the backend does not advertise the updated 10% invoice-deduction terms. There is no polling or public signature endpoint.

Version 5 specifies 10% of each approved student's first tuition payment, excluding processing fees; later instalments and renewals do not earn another share. Admin can use **Apply 10% organisation share** to fill the existing per-student deduction amounts, then review the invoice before generating the link. Staff must check payment history before applying a first-payment share. Net tuition and retained deductions continue to be stored separately. Older version 3 signed documents and approval notifications remain supported without rewriting PDFs. No separate payout, bank collection or Paystack split is introduced.


## Organisation course duration and class requests (5 November 2026)

New agreement receipts use `organisation-partnership-2026-11-05-v5`. Tuition is non-refundable. Each class lasts 10 weeks; Falowen access lasts six months from account activation, including time remaining after early class completion. Students may request class changes during that contract, subject to approval and availability, without restarting or extending access. Historical signed receipts remain unchanged.

The organisation student form loads the existing public class catalogue on demand (no private class reads or polling), then selects each student's level and class/start date. New clients submit schemaVersion 2 with required requestedClassId, requestedClassName and requestedClassStartDate. These are unverified preferences visible in Admin review and preserved on approved pending students, not an automatic class assignment. Staff confirm current availability and configure the canonical class and contract before activation. Older submissions remain reviewable without these fields. This change does not alter existing account expiry or payment enforcement.

Deploy the new Admin agreement API before the public page: clients require metadata for non-refundable tuition, 10 class weeks, six access months and account-activation start before signing. The 10% first-tuition invoice deduction remains unchanged.
